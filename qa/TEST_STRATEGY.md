# Production test strategy — Jubis Marketing ERP

Prepared 2026-10-12. Source: user-supplied `Jubis_Marketing_ERP_System_Inventory.pdf`, checked against this checkout. Scope: nine modules, seven roles, Laravel12/Vue3/Inertia2, MySQL8 production, SQLite deterministic regression, PayMongo, Lalamove simulation and SMTP/background stock alerts. All tests below are release requirements or planned scenarios unless the execution report explicitly records a pass. No certification of tax/legal compliance is implied.

Capture screenshots/traces on browser failure and sanitized structured logs for integration failures. Run 360px,768px,1440px layouts and current Chrome/Firefox/Safari-equivalent WebKit in release staging; verify keyboard navigation, focus/error announcements and 200% zoom. ## 2. API and integration testing matrix

[ENDPOINT_MATRIX.csv](ENDPOINT_MATRIX.csv) and [data/endpoint-matrix.json](data/endpoint-matrix.json) contain one explicit row per method and registered endpoint, including schemas, happy assertions, field/type failures, endpoint-specific abuse/boundary cases, authorization, bursts and failure/timeout injection. The Markdown version is a readable summary. Generate them from the live route registry with `php qa/export-routes.php` followed by `node qa/build-matrix.mjs`. Five registered controller actions are missing; no invented happy contract hides those defects.

### Protocol expectations

The app is primarily session-authenticated web/Inertia routes, including the routes named `/api/…`; Sanctum installation does not mean bearer-token authentication is implemented. GET views return HTML200 or Inertia JSON200; CSV/PDF return binary/text200; CSRF-cookie returns204. Successful form mutations usually return302 (303 after an Inertia non-GET redirect may be appropriate). A REST create201 is not the current contract; if a versioned API is added, require201+Location for creates. JSON field validation is422, malformed JSON may become422 via missing fields or400 with an explicit parser; it must never mutate or expose a stack trace. Browser validation redirects302 with a session error bag. Business rejections such as insufficient stock often redirect302 with `flash.error`; assert the error and unchanged DB, not just the status.

No session => JSON401 / browser302 to login; authenticated role denied =>403; missing resource =>404. Owner-denied PDF/terms=>403; foreign cart/RMA lookup=>404 to avoid existence disclosure. Missing/invalid CSRF on a web mutation=>419 and no write. Webhook bypasses CSRF and must authenticate independently by signature. Method not supported=>405; oversized body must fail413 at the chosen server boundary, without a partial document. HEAD must match GET headers with empty body; OPTIONS/CORS must deny unapproved origins without credentials leakage. Never disable CSRF or route middleware broadly just to run API tests.

The role oracle comes from the PDF and current middleware: super_admin/admin all admin areas; sales quotes; finance quotes/invoices/RMA/reports; purchasing inventory/suppliers/PO/shipments; warehouse inventory/shipments; client only own workflows. The PDF omits purchasing from its shipment row while actual code grants it; record that difference for business-owner acceptance. Auth-only cart routes currently accept all logged-in roles at middleware level; test role abuse as an explicit requirement, not a claimed implemented client-only restriction. PDF access allows only owner/admin in code; super_admin/finance expectations need an explicit corrected authorization contract. Deny role supplied through registration/profile; role/ownership decisions must come from the session and database, never hidden UI buttons.

For every endpoint: happy request with precise resource values; omit each required field individually and all fields; null/wrong type/extra field; malformed body; nonexisting and another client's ID; each of seven roles; session absent/expired; repeated request; read-after-write; error path leaves before-state unchanged. Include route binding on PUT/PATCH independently. Compare schema to validated fields and model serialization: passwords, remember tokens, provider secrets and server paths cannot be returned. Route matrix is a planned catalog; current execution covers a subset of HTTP endpoints plus all registered admin role boundaries, not all 81 full endpoint workflows.

### Rate, load and timeout acceptance

Login currently allows five wrong attempts per email+IP then returns422 validation; verify lockout, retry-after message, expiry at60s, successful login reset and distributed abuse. Verification has6/min route throttling; seventh=>429, controlled reset, distinct legitimate sessions unaffected. Contact/registration/reset/mock/payment endpoints lack explicit comparable limiter policy: require risk-based limits, 429+Retry-After and no duplicate financial or email effects for an enforced limit. This is an unclosed security gate; do not expect every GET to return429 when the app has no limiter.

On disposable staging ramp1,10,50 requests/s for60s per endpoint and a20-minute mixed business soak. Proposed initial SLOs for owner approval: interactive reads p95<=2s, writes<=3s, export<=10s for10k rows, <1% server errors, no lost or duplicated writes; capacity/hardware must be recorded. These are proposed budgets, not measured production claims. Gateway/courier connect timeout<=3s and total<=10s, bounded exponential retry with jitter only for safely idempotent operations; webhook acknowledges within5s. SMTP sends must have bounded timeout and observable retry state. Cancel a slow browser request, inject SQL lock timeout/deadlock, and retry once: the document/stock/audit result remains atomic and no external booking/payment happens twice. Do not load-test the public tunnel or real payment gateway.

## 3. ERP standards and data integrity checks

### Financial invariants

Use decimal arithmetic or integer centavos as the oracle; proposed rounding: round each `quantity * quoted_price` to2dp, sum lines for subtotal, round subtotal*0.12 to2dp, total=subtotal+VAT. Agree and freeze the rounding policy with finance before release; never compare floats with a broad tolerance that hides a1-cent error. Monetary columns currently use decimal(12,2): maximum9,999,999,999.99, plus appropriate smaller product-price limits from schema; verify MySQL strict-mode boundaries, overflow and third-decimal rejection/explicit rounding. SQLite cannot validate those production storage constraints. Test0.01,0.29,0.99,100.005,9999999999.99 and overflow, comma decimal strings, scientific notation, NaN/infinity, null and negatives. Quantity is an integer:0,-1,1,stock,stock+1,1.5,PHP/database integer max and max+1.

Invoice totals must equal the approved quote snapshot, not the current product price; later edits/deletions cannot rewrite historical financial values. `0 <= amount_paid <= total_amount`; paid means exact full balance; partial means0<paid<total. Record each payment exactly once and derive balance from immutable postings; concurrent payments cannot overwrite one another. Net30 applies only to aggregate qty>=1000, owner and permitted credit state; due date is acceptance date+30 calendar days in Asia/Manila, immutable on retry, and cannot reopen a paid invoice. Proposed state machine: unpaid -> partially_paid/paid/on_terms; on_terms -> partially_paid/paid/overdue; paid terminal unless authorized documented reversal. Status rejections must show a clear conflict and leave all values unchanged. Credit-status restrictions are a proposed gate beyond the PDF's quantity-only statement.

The repo has no general-ledger/journal/double-entry bookkeeping module. Do not report debit/credit balance as passed. If required for production ERP accounting, treat it as a feature gap: every posted journal `SUM(debits)=SUM(credits)` in centavos; AR debit = gross invoice, sales credit = subtotal, VAT payable credit = VAT; receipt cash debit = amount, AR credit = amount; refunds use linked reversing entries, never delete postings. Finance must define revenue recognition, tax treatment and refund/credit-note rules. Current `paid invoice sales` is a collection/status metric, not an audited revenue ledger. Legal/tax sign-off belongs to the business's accountant, with real company/TIN configuration; placeholders cannot pass a tax invoice requirement.

### Inventory, documents and transactions

For a freshly seeded item: closing available stock = opening stock + SUM(committed signed movement quantities). Current quote submission immediately subtracts stock and labels it sale/reservation; this is the available-stock oracle, not separate physical on-hand plus reservation ledgers. Shipping and repeated payment must not subtract it again. Reject restores once; canceled/reopened quote must follow an approved state transition without creating inventory. PO received adds each item once, reversals remove only unconsumed reversible units and never make stock negative. RMA request itself has no approved refund/restock effect. Master folders must not be counted alongside actual variant stock if they are display-only.

Require one invoice per approved quote, one shipment per invoice under current business semantics and one RMA per invoice; enforce database uniqueness plus idempotent application transitions. IDs/document numbers must remain unique under concurrency and after soft deletion; visible invoice number and download filename must refer to the same immutable business document. Validate item FK existence AND active/nondeleted/saleable status. Preserve financial history when deleting users/suppliers/products: either block deletion while referenced or soft-delete while retaining historical snapshots.

Atomicity: failure on any item after the first stock mutation rolls back the whole quote/status/movements; PO header/lines/total/receipt movement commit together; RMA header/all lines commit together; invoice transition/payment posting/audit commit together. Inject failure on the second DB insert/update and verify counts, values, status, timestamps and audit unchanged. Provider calls and SMTP are not rolled back by SQL: use an outbox/idempotent retry contract, reconcile external results and never return fake success if a service failed. The supplied rollback tests verify quote stock and PO inserts; other transaction paths remain separate gates.

### Concurrency cases (MySQL8, InnoDB, multi-worker server)

Use synchronized requests on independent authenticated sessions/processes. Run each at least20 times with fresh fixtures. A barrier or held row lock must prove overlap, not just simultaneous client scheduling. Record SQL lock wait/deadlock handling and final DB evidence. The included Promise.all harness can exercise requests but is not a proof of collision without server timing/lock evidence.

| ID / priority | Setup and competing actions | Required result |
|---|---|---|
| CON-01 P0 |Stock5, A/B drafts qty4; both submit |Exactly one pending, one draft with insufficiency; stock1, one -4 sale movement, no partial invoice |
| CON-02 P0 |Same draft submitted twice by same client |One transition/reservation only; stock decremented once; one movement per line |
| CON-03 P0 |Quote reserve2; two staff approve or approve/reject together |Single invoice/reference; authorized final state; stock reconciles to one chosen transition, no duplicate restoration |
| CON-04 P0 |Invoice total224; simultaneous payments100 and124 |Paid224, two unique postings; no lost increment; repeat retry has no third posting; excess225 rejected |
| CON-05 P0 |PO qty5; two receiving requests or receive/reverse race |One net receipt according to final committed state; audit once; no stock underflow |
| CON-06 P1 |Two shipment creates for same paid invoice |One shipment/booking/mail; loser409/422; database uniqueness enforced |

### Export and analytics verification

PDF: compare each product/SKU/qty/quoted price/line total, subtotal,VAT,grand total,amount paid,balance,shipping fee,date,client/address and invoice number against a DB snapshot. Shipping must be represented in the ledger/payment amount if included in the export; the PDF cannot invent a different payable total. Verify Content-Type/attachment, `%PDF-`, nonempty extraction, full strings/Unicode, first/last rows and multipage headers/footer with1,50,200 lines, long SKU/address, large amounts and all statuses. Extract actual generated PDF text and render all pages at release; current gate checks template values and authorized download, not complete binary layout. Check authorized role/owner access, correct filename and absence of private data. Placeholder company/TIN is a blocker for formal tax-invoice use.

CSV: parse with a CSV parser, not split(','). Compare header/column count, count of intended nondeleted rows, ID/SKU uniqueness, full-set sums, Unicode/BOM/encoding, embedded commas/quotes/newlines, formulas `=,+,-,@` (also leading tab/CR), numeric types and exact2dp prices. No truncation at UI's12/15 row pagination. Distinguish full export from filtered export and test that declared scope. Formula-like user text must be neutralized when opened in a spreadsheet. XLSX export is not implemented; opening CSV in Excel is not an XLSX test. If required, gate XLSX type/cell formatting/formulas/row count and exact totals before adding that feature to coverage.

Reports: independently compute paid invoice sales, outstanding AR across unpaid/partial/on_terms/overdue, procurement sum under agreed statuses, inventory stock*price, six calendar month buckets with zero months, top10 product totals, brand totals and funnel counts. Compare dashboard/reports to the same snapshot/filter definitions and prevent double-counting variant parents. Test six-month boundary and monthend at Manila midnight, leap day, future records, reversal/refund, soft deletion and no data. Current reports exclude partial/on_terms from open receivables; treat discrepancy as a finance gate rather than copy implementation into expected results.

## 4. Security and compliance baseline

Use OWASP ASVS5.0 Level2 as a target control catalog and WSTG/cheat-sheet test methods. This is a scoped verification baseline, not an ASVS compliance claim: map exact versioned requirements and attach evidence for every applicable control before stating conformity. Primary references: [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/), [Business Logic Security](https://cheatsheetseries.owasp.org/cheatsheets/Business_Logic_Security_Cheat_Sheet.html), [Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html), [Laravel12 database transactions](https://laravel.com/docs/12.x/database#database-transactions).

| Security case | Procedure | Required acceptance / evidence |
|---|---|---|
| SEC-IN01 SQL injection |Submit `' OR 1=1 --`, escaped quotes, UNION-like literals in catalog/admin searches, IDs and names on disposable data |No expanded unauthorized results, no SQL trace, bound parameters, no changed rows; list assertions plus logs |
| SEC-IN02 Stored/reflected XSS |Product/company/notes/address/settings/contact fields with script,img-onerror,SVG payloads; view catalog/admin/mail/PDF/tracking |Text escaped; no script executed/pageerror; CSP adequate; inspect context-specific URLs too; no raw v-html from user data |
| SEC-IN03 Uploads |2MB boundary, renamed php/html/SVG polyglot, same-second duplicate original filenames, traversal-like filename |Only intended safe image types/content accepted, no executable public file, unique stored name, no overwrite/traversal; files cleaned from QA storage |
| SEC-AU01 Session fixation/replay |Set old session before login; compare ID after; logout then reuse cookie; expire idle/absolute lifetime; password reset/change |New ID on login, old cookie denied after logout, expired session401/302, no privileged cache; explicit token/session invalidation policy |
| SEC-AU02 Cookie/TLS |Inspect real HTTPS staging cookies/headers, mixed content and localtunnel proxy behavior |Secure,HttpOnly session cookie, appropriate SameSite, no credentials in URL/storage, HTTPS redirects/HSTS per deployment, trusted proxies correct; do not weaken CSRF for tunnel |
| SEC-AU03 Reset/verification |Expired/reused/foreign reset token; bad hash/signature on verification; unknown-account reset response |No token replay/privilege change, expiry effective, rate limited, no account enumeration, secrets absent from response/logs |
| SEC-RB01 RBAC/IDOR |All7 roles on each endpoint/method; guess another client's cart/invoice/PDF/RMA/terms; directly call hidden admin buttons |401/403/404 contract and no financial/stock mutation; owner check server-side; no privilege supplied by body |
| SEC-RB02 Escalation |Inject role/credit_status in register/profile; modify staff role mid-session; demote last superadmin; delete staff/customer with history |No mass assignment elevation; old sessions immediately honor current role; durable admin access; history survives |
| SEC-PAY01 Payment authenticity |Unsigned/bad/stale/mode-mismatched webhooks; direct guest/foreign simulator requests; production mock URLs |Provider signature and business data verified before posting; mock routes absent in production; no financial effect on failed auth |
| SEC-PR01 Data/secrets |Inspect Inertia shared props/public settings, exports/logs/errors/source maps, `.env`, backup files and dependency audit output |No passwords/API keys/SMTP secrets/payment signatures/customer address leakage; least privilege DB/service accounts; backups encrypted/access-controlled |
| SEC-CS01 CSRF/CORS/redirect |Remove/tamper CSRF; cross-site form; arbitrary Origin; hostile payment/tracking URL |419/no write; credentialed CORS allowlist only; no open redirect/phishing; URL scheme/host allowlist |
| SEC-AD01 Audit integrity |Quote/payment/receipt/reversal/stock/user/role/settings/RMA/shipment actions and failures, including provider/system actor |Append-only durable event with timestamp/timezone, actor/system ID, entity/business ref, action,outcome,before/after, correlation/event ID; no secret payload; clients cannot alter/delete audit |

`stock_movements` is a partial audit mechanism; it does not establish a full financial/role/settings audit trail. Assert movement user_id, created_at, signed quantity, reference_id and action; require durable events for the other critical actions. Log rejection/authorization attempts without secrets. Preserve historical user attribution after account deletion. Agree retention/privacy/access with the business; no jurisdiction-specific compliance is certified by these tests. OWASP control target and financial invariants are engineering criteria, not legal advice.

Additional operations: production APP_DEBUG=false, no default/shared test passwords, rotate sandbox/production credentials separately, dependency vulnerability scan with triage, restrict public admin/webhook traffic appropriately, monitor failed callbacks/negative stock/duplicate docs/queue failures, restore a sanitized backup to an isolated environment and reconcile, and exercise deployment/rollback without data loss. These are explicit evidence gates and have not been executed by the local PHPUnit run.

## 5. Execution checklist and severity framework

Use [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md). Run isolation/bootstrap -> baseline -> release-gates -> Vue/build -> browser -> MySQL reports/races -> integration sandbox/faults -> exports/security/backup -> sign-off. Never accept zero tests, skipped critical coverage or a suppressed gate failure as a pass. Each case is PASS/FAIL/BLOCKED/NOT RUN/NOT APPLICABLE with a reason and artifact; every failure has severity, owner and retest evidence.

Release rule: all P0/P1 closed and retested, required MySQL/integration/security evidence complete, no unexplained financial or inventory discrepancy, all critical flows work for all roles, and P2 exceptions have named owner/expiry/business approval. RMA approve/reject/refund, general ledger and XLSX are absent features, not passing cases; approve scope exclusion explicitly or implement before claiming full ERP coverage. Current local execution is evidence of defects and baseline behavior, not a production-ready approval.
